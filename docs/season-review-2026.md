# 2026 시즌 참가 결과와 운영 회고

2026 스탯티즈 대학생 승부예측 대회에서 데이터 처리·확률 예측·제출·결과 추적을 함께 운영한 경험을 정리했습니다. 공개 참가 결과와 보관 기록에서 확인한 판단을 연결하고, 대회를 통해 얻은 점으로 결산을 마무리합니다.

[문서 목록](README.md) · [운영 기록 분석](operations-review.md) · [지표 정의](evaluation-guide.md)

모델의 입력·학습·서빙 경로는 [모델링 구조](modeling.md), 실제 기간별·팀별 결과와 동일 경기 비교는 [예측 성능 결산](prediction-performance.md)에 정리했습니다.

## 참가 결과와 담당 범위

2026년 10월 14일 [중앙대학교 최강이조 참가 페이지](https://www.statiz.co.kr/prediction/?m=university_detail&ptt_idx=70)를 조회했습니다.

| 항목 | 확인한 내용 |
| --- | --- |
| 팀 | 중앙대학교 최강이조 · 4인 팀 |
| 공개 성적 | 16위 · 시즌 적중률 54.6% · 게임 참여수 689경기 · ALL KILL 5회 |
| 본인 역할 | 데이터 처리·모델 개발·웹 대시보드·서버 및 자동 제출 운영 전반 참여 |
| 개인 기여율 | 별도로 산정하지 않음 |
| 공개 산출물 | 참가 결산, 분석·운영 설명, 운영 UI 정적 기록, 독립 합성 재현 예제 |

성적은 초반 수동 제출과 이후 자동 운영, 여러 모델이 포함된 팀 전체 기록입니다. 게임 참여수를 적중률 분모로 확인한 것은 아니므로 성공 경기 수를 역산하지 않았습니다. 조회 시점의 표기를 최종 심사·수상 발표로 바꾸어 쓰지 않습니다.

## 참가 과정

초반에는 수동으로 제출했고, 대회 시작 이후 원격 서버 운영을 도입했습니다. 일정에 따른 예측 실행, 모델 선택, 제출 응답 기록, 실제 결과와의 매칭, 대시보드 조회를 연결했습니다. 수동에서 자동으로 전환한 정확한 날짜와 초기 경기별 접수 기록 전체는 대조되지 않아 임의의 전환 시점을 쓰지 않았습니다.

경기 시작 30분 전 실행은 API의 당일 라인업이 60–30분 전에 갱신되는 운영 관측을 반영한 선택입니다. [공식 정책](https://statiz.co.kr/board/?b_code=10000&b_idx=4294959131&m=main&mode=view)의 경기 15분 전 마감까지 계산과 제출 응답을 확인할 시간을 두었습니다.

시즌 결산 시점에는 `predictor_v13`의 `pit_lgbm_v1` 직접 확률 LightGBM이 선택되어 있었습니다. 과거 Rule·Elo/Glicko-2·LightGBM 스태킹, 실제 운영 예측, 사후 재구성 점수는 서로 구분해 검토했습니다.

실제 원장과 내부 분석 파일은 공개하지 않았습니다. 공개 예제는 같은 평가 원칙을 독립적인 가상 사례로 재현하며, 가상 점수를 대회 성과에 더하지 않습니다.

## 관측에서 판단으로 이어진 사례

### 1. 예측이 맞았는지와 접수됐는지를 분리

**관측:** 주최 측 참가 기록, 보존 예측, 접수 응답의 대상 기간과 경기 범위가 같지 않았습니다. 초기 수동 제출과 이후 자동 운영이 함께 포함되어 있었습니다.

**처리:** 일정에서 출발해 예측 없는 경기도 남겼고, 여러 접수 이벤트는 마감 전 마지막 성공 한 건으로 정리했습니다. 미확인 접수와 대조 후 확인한 미접수를 구분했습니다. 복구하지 못한 원본 확률을 사후 재실행으로 채우지 않았습니다.

**배운 점:** 지표를 계산하기 전에 관측 단위와 분모, 제외 조건, 증거의 상태를 정해야 성적 차이를 설명할 수 있습니다. [분모가 달라지는 9경기 예제](evaluation-guide.md)에 이 판단을 재현했습니다.

### 2. 실행 설정과 실제 처리 시각을 구분

**관측:** 30분 전 실행 목표와 경기별 예측 생성 완료·성공 응답 시각 사이에는 차이가 있었습니다.

**처리:** 보존 성공 응답과 최종 일정을 대조해 마감 여유를 계산했습니다. 생성 시각과 접수 시각이 모두 있는 기록만 경과시간 분석에 사용했고, 시각 누락을 0초로 채우지 않았습니다.

**배운 점:** 예측 실행 성공과 제출 성공은 다른 사건입니다. 생성→접수 경과시간도 모델 전체 계산시간이나 네트워크 지연 자체를 뜻하지 않습니다. 라인업 갱신을 기다리는 이유와 마감 여유를 함께 설명하는 것이 운영 판단의 핵심이었습니다.

### 3. 모델 차이를 동일 경기에서 해석

**관측:** 모델별 운영 기간이 달라 대진과 입력 환경도 달랐습니다. 같은 경기에서 비교해도 관측된 차이에 불확실성이 남았습니다.

**처리:** 모델 이름별 평균 성적만 비교하지 않고 동일 경기의 확률·적중 차이와 단순 기준을 대조했습니다. 모델 확률 차이 구간, 월별 편차, 날짜·7일·14일 묶음의 민감도를 함께 확인했습니다.

**배운 점:** 관측된 순증이나 유리한 일부 구간만으로 안정적인 우위를 주장할 수 없습니다. 팀별 표에서 한 경기가 양 팀에 포함되는 점도 고려해 표의 행 수를 독립 경기 수로 해석하지 않았습니다.

### 4. 입력 정의를 성능 해석의 출발점으로 삼음

**관측:** 과거 재구성 입력과 경기 전 보존 입력의 기본값·분포가 같은 의미인지 점검할 필요가 있었습니다. 일부 기록은 당시 원본 보존 여부를 따로 확인해야 했습니다.

**처리:** 변수의 정의·분모·누적 종료일·가용 시각을 대조하고, 원시 카운트와 표본 수를 함께 해석했습니다. 입력 중요도를 인과효과로 읽거나 사후 보정 진단을 새 성능 향상으로 보고하지 않았습니다.

**배운 점:** 같은 변수 이름도 생성 시점과 기본값 처리에 따라 다른 입력이 될 수 있습니다. 확률 품질, 승자 선택, 제출 완결성 역시 별도로 해석해야 했습니다.

## 결산에서 확인한 범위

시즌 참가·운영 경험, 원본 보존과 전달본 검사, SQL 대조·시간 감사·모델 비교, 공개 예제와 문서를 정리했습니다. 이는 보관 증거를 바탕으로 참가 과정을 설명한 결산입니다.

초기 접수 기록의 완전성, 주최 측 사후 자료 제출 접수, 최종 심사·수상 여부는 이 결산의 확인 범위와 구별합니다. 또한 자동화 전후의 비교 가능한 업무시간을 측정하지 않았으므로 시간 절감률을 성과로 만들지 않았습니다.

## 대회를 마치며

이 프로젝트에서 배운 핵심은 예측 모델의 출력이 참가 성적으로 이어지기까지 여러 단계의 데이터와 운영 기록이 필요하다는 점입니다. 입력 시점과 경기번호를 맞추고, 제출 응답을 보존하고, 같은 경기에서 모델을 비교해야 결과를 설명할 수 있었습니다.

데이터·모델·웹·서버에 걸쳐 참여한 경험을 결산하면서, 기술 목록보다 **어떤 문제를 확인했고 어떤 근거로 판단했는지**를 중심으로 기록했습니다. 공개본은 그 판단을 읽고 작은 예제로 검증할 수 있는 대회 참가 기록으로 정리했습니다.
