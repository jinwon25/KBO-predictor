## 수동 제출과 원격 자동 운영

참가자의 회고에 따르면 대회 초반은 수동 제출이었고, 원격 서버 운영은 대회 시작 이후 도입됐습니다. 수동 제출 시기의 기록, 미제출을 실패로 계산하는 공식 평가, 이후 서버에 보존된 예측의 범위가 다를 수 있습니다. 원격 전환의 정확한 날짜와 초기 경기별 접수 원장 전체는 아직 대조되지 않았습니다.

운영 원장에 기록이 없다는 이유만으로 실제 대회에 제출하지 않았다고 단정하지 않습니다. 반대로 모델을 사후 재실행해 생성한 확률을 당시 제출값으로 보완하지도 않습니다. 초반 수동 제출을 포함한 전체 팀 기록과 자동 운영 구간의 모델 평가를 나눠 해석하는 것이 필요합니다.

[2026년 3월 27일 공식 정책](https://statiz.co.kr/board/?b_code=10000&b_idx=4294959131&m=main&mode=view)은 미제출을 실패로 계산하며 무승부·취소·DH 2차전을 제외합니다. 마감 전 마지막 접수 확률을 사용하고 정확히 50%이면 실패입니다. 이러한 판정 조건과 기록 범위 차이는 내부 대시보드 수치와 공식 페이지 수치가 다른 이유가 될 수 있지만, 차이 전체의 경기별 원인은 접수 원장 대조 전까지 확정하지 않습니다.

## 어떤 문제를 다뤘는가

| 문제 | 구현·점검한 접근 | 남은 과제 |
| --- | --- | --- |
| 경기 일정에 맞춘 반복 작업 | 일정·실행 시점·모델 선택·제출 이력을 연결한 서버와 대시보드 | 접수 증거와 예측 원장을 경기번호별로 끝까지 대조 |
| 모델 변경과 성적 해석 | 모델 적용 기간·경기 수를 표시하고 같은 경기의 예측을 비교 | 후보 선택에 쓰지 않은 이후 기간에서 검증 |
| 입력 자료의 시점 | 경기 전 보존 입력과 사후 재구성을 구분해 점검 | 변수별 원천·누적 종료일·이용 가능 시각의 계약 고정 |
| 승률과 실제 결과 추적 | 확률·승자·점수·제출 상태·제외 조건을 분리 | 공식 분모와 보존 예측 분모의 일별 연결 |
| 재현성과 원본 보존 | 모델·입력·예측·접수·검증 산출물을 별도로 보관 | 입력이 덮어써지지 않는 스냅샷과 고정 평가 자료 유지 |

현재 서빙은 `predictor_v13`의 `pit_lgbm_v1` 모드이며 직접 확률 LightGBM을 사용합니다. 과거 스태킹 설계, 사후 재구성 점수, 실제 운영 예측을 같은 성능 기록으로 합치지 않습니다. 팀 전체의 공식 기록으로 특정 모델의 우월성이나 개인 기여율을 계산하지 않았습니다.

## 연구에서 얻은 판단

시즌 점검은 모델의 크기보다 검증 단위와 입력 정의를 먼저 고정할 필요를 보여줬습니다. 과거 재구성의 기본값과 실전 입력의 정의가 다르면 학습 알고리즘을 교체해도 같은 의미의 변수를 학습했다고 보기 어렵습니다. 선발투수 비율은 원시 카운트·표본 크기를 함께 기록해야 하며, 시즌·구장·득점 환경의 차이는 시간 조건을 지킨 상대 지표 후보로 검토합니다.

확률 품질, 승자 선택, 제출 완결성을 각각 평가합니다. 확률 보정으로 확신의 정도를 바꾸는 것과 승자 판별의 개선은 서로 다른 실험입니다. 동일 경기 비교에서 관측한 차이에는 불확실성 구간을 붙이고, 팀별로 같은 경기를 두 번 포함한 집계를 독립 표본으로 취급하지 않습니다. 구체적인 가설·설계·기각 조건은 [다음 연구 계획](research-plan.md)에 있습니다.

## 확인 범위와 보존 원칙

이 문서에 수치로 재기재한 성적은 주최 측 공개 팀 페이지의 요약입니다. 내부 경기별 확률·원천 통계·실제 접수 원장·학습 아티팩트는 공개 저장소에 옮기지 않았습니다. 상세 내부 결산과 원본 산출물은 사후 검증을 위해 별도로 보존합니다.

이 저장소의 독립 합성 데모는 채점 경계와 화면 상태를 설명합니다. 가상 팀·가상 모델의 데모 점수를 실제 참가 성과에 더하지 않습니다. 운영 경로 전체의 규정 적합성, 별도 참가 서약·FAQ와 추가 공개 권한에 관한 확인 범위는 [데이터·공개 정책](data-policy.md)을 따릅니다.
