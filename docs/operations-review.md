# 30분 전 실행의 근거와 운영 기록 대조

2026-10-14 시즌 결산에서 **보관된 운영 기록을 대조**했습니다. 완료 경기의 일정·보존 예측·접수 응답을 SQLite로 대조하고, 제출 여유와 두 모델의 불일치 구간을 분석했습니다. 실제 원장·경기별 수치·내부 분석 파일은 별도 보존하며, 공개본에는 판단과 독립 합성 재현 코드를 담았습니다.

[시즌 결산](season-review-2026.md) · [지표 정의](evaluation-guide.md) · [문서 목록](README.md)

## 왜 경기 시작 30분 전인가

운영자는 API의 당일 라인업이 경기 시작 **60분 전에서 30분 전 사이에 갱신되는 것을 관측**해 30분 전 실행을 선택했다고 설명했습니다. 이는 2026-10-14에 확인한 운영 판단의 근거이며, 공급자가 보장한 갱신 시각이나 모든 경기의 완전한 관측 통계는 아닙니다.

여기서 T는 예정된 경기 시작입니다. T−30은 **예측 실행 목표**이며 예측 생성 완료·접수 완료 시각과 다릅니다. [공식 대회 정책](https://statiz.co.kr/board/?b_code=10000&b_idx=4294959131&m=main&mode=view)의 T−15 마감까지 명목상 15분의 처리 여유를 둡니다.

| 시점 | 의미 | 결산에서 구분한 점 |
| --- | --- | --- |
| T−60∼T−30 | 운영자가 경험한 라인업 갱신 구간 | 모든 경기에서 양 팀 라인업이 완전하다는 보장은 아님 |
| T−30 | 기존 예측 실행 목표 | 계산·대기·접수 시간이 남아 있음 |
| 예측 생성 완료 | 경기별 확률이 만들어진 시각 | 실행 시작이나 입력 수집 시작과 다름 |
| 제출 성공 응답 | 보존 클라이언트가 성공 응답을 기록한 시각 | 주최 측 전체 원장과 별도 증거 |
| T−15 | 대회 제출 마감 | 실제 접수 완료와의 차이를 측정 |

**T−30 설정은 라인업 갱신을 기다리는 시간과 마감 전 처리 여유를 함께 고려한 운영 선택**이었습니다. 보존 성공 응답에서 실제 마감 여유를 점검했으며, 과거의 모든 라인업 갱신 시각을 관측한 자료는 없어 설정의 최적성까지 주장하지 않았습니다.

## 보관 자료로 확인한 내용

| 실행한 분석 | 관측과 판단 | 남은 한계 |
| --- | --- | --- |
| 일정 중심 SQL 대조 | 완료 경기 수·보존 예측 수·성공 접수 증거 수가 기존 결산과 일치 | 취소 이력·일정 버전 전체를 모델링한 운영 데이터웨어하우스는 아님 |
| 접수 시간 감사 | 성공 응답이 있는 완료 경기에서 최종 일정 기준 마감 여유를 확인. T−30 실행 목표와 실제 접수 사이에 차이가 있음 | 기록 시작 이전 접수·모든 실패를 대표하지 않음 |
| 생성→접수 시간 | 두 시각과 확률이 일치하는 부분집합만 계산 | 생성 시각이 없는 기록을 0초로 대체하지 않음. 전체 추론 시간도 아님 |
| 모델 불일치 구간 | 현·이전 모델의 확률 차이를 구간으로 나눠 동일 경기 적중·Brier 비교 | 큰 차이 구간의 관측 개선만으로 전환 규칙을 만들지 않음 |
| 블록 크기 민감도 | 날짜·7일·14일 묶음에서 모델 차이의 불확실성 확인 | 긴 블록은 개수가 적고, 팀·시리즈 의존성을 완전히 제거하지 못함 |

이번 모델 진단은 이미 확인한 시즌 자료의 **탐색적 회고 분석**입니다. 독립 검증이나 새 후보 성능 향상으로 표현하지 않습니다. 새 학습·보정·모델 교체는 실행하지 않았습니다.

## 공개 SQL 예제를 실행하기

추가 패키지가 필요하지 않습니다.

```bash
python -m demo.operations_audit
python -m unittest discover -s tests -v
```

[구현](../demo/operations_audit.py)은 독립 합성 4경기와 5개 응답 이벤트를 사용합니다. 기존 [9경기 지표 예제](evaluation-guide.md)와 별도의 자료입니다.

| 합성 경기 | 이벤트 | 대조 결과 |
| --- | --- | --- |
| A | 마감 전 성공 2건, 마감 후 실패 1건 | 마지막 마감 전 성공 1건 선택, 경기 수는 1 |
| B | 실패 응답만 보존 | 접수 미확인. 다른 성공 접수가 없었다는 증명은 아님 |
| C | 무승부, 예측·응답 없음 | 일정에는 남기고 채점 대상에서는 제외 |
| D | 마감 후 성공으로 기록된 응답만 존재 | 시간 불일치 점검 대상으로 분리, 마감 전 성공으로 세지 않음 |

출력은 일정 4건, 채점 대상 3건, 보존 예측 3건, 마감 전 접수 확인 1건입니다. A의 마감 여유는 12분이고 생성→접수 경과시간은 120초입니다. **모두 합성 예제 수치이며 실제 운영 성능과 무관합니다.**

세 테이블의 단위는 다음과 같습니다.

- `schedule`: 경기당 일정·결과 한 버전. 실사용 어댑터는 날짜와 원본 경기번호로 키를 구성합니다.
- `retained_prediction`: 경기당 보존 예측 한 건. 과거의 모든 실행 이력을 복원했다고 가정하지 않습니다.
- `receipt_event`: 제공된 응답 이벤트 한 건. 마감 전 성공을 먼저 추린 뒤 `ROW_NUMBER()`로 한 건을 선택합니다.

일정에서 왼쪽 결합하므로 예측 없는 경기도 남습니다. 중복 키·고아 키·잘못된 확률·시간대 없는 시각은 입력 오류로 처리합니다. 같은 성공 시각의 이벤트가 겹치면 결정적 ID 순서로 선택하되 별도 경고 수를 남깁니다. 이때 실제 최종 접수 순서는 원장과 대조해야 합니다. 예제는 마감 정각을 포함하는 가정이며 서버의 경계 구현을 인증하지 않습니다.

`unconfirmed`는 미제출 확정이 아닙니다. 이 모듈의 접수 집계는 입력된 일정 전체 기준이며 무승부·취소 제외 후 대회 점수를 계산하는 함수가 아닙니다. 공식 성적 계산에는 [지표 정의](evaluation-guide.md)의 분모·제외 조건과 별도의 접수 증거 검토가 필요합니다.

## 결산에서 얻은 점

일정과 원장을 연결한 결과, 예측 생성·접수·결과 적중을 각각 기록해야 운영 성과를 설명할 수 있었습니다. 실행 목표와 실제 처리 시각의 차이, 누락 시각, 접수 미확인을 별도로 다룬 것이 이번 결산의 핵심입니다.

완료 경기 범위의 SQL 대조·시간 감사·모델 비교와 합성 재현 예제를 정리했습니다. 초기 원장의 확인 범위와 실제 입력의 시각 증거에 따른 한계는 분석 결과와 함께 남겼습니다.
